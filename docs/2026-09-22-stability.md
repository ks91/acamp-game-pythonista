# 9/22 出発前の安定性確認

## 今回の変更

- red: 攻撃のたびに戦闘 UI を破棄していた処理を変更。通常ターンは既存のボタンと表示を更新する。武器消耗・勝敗確定などの画面更新は `ui.delay` でタップのコールバックの後に実行する。処理中の重複入力と古い画面からの入力は無視し、報酬の二重処理を防ぐ。終了時は位置追跡を停止する。
- yellow: 起動時の自動リセットを廃止し、既存の進行を読み込む。明示的なリセットは共通 API クライアント経由にし、ギャラリーで選んだゲーム・モードを通信に含める。
- 攻撃力・報酬・キャラクター・謎・ゲームルールは変更していない。ただし red の処理待ち（0.05 秒）の間に届いた追加タップはまとめて無視する。

red のネイティブクラッシュは Mac では再現・解消確認できていない。ボタンをそのコールバック内で破棄する経路と毎ターンの再生成を除いた対策であり、根本原因の確定ではない。Pythonista の `ui.delay` の仕様は [公式 UI ドキュメント](https://omz-software.com/pythonista/docs-3.4/py3/ios/ui.html) を参照。

実機からの報告：red の確認スクリプトは良好。確認後にギャラリーから yellow を選んだ際、一度 Pythonista 全体が終了したが、その後は再現していない。yellow の起動経路には画像読み込みはない。ゲーム選択時の稀なクラッシュは原因未特定・未解決として扱う。

### 残る懸念

- red・purple・pink の進行は、下記の追加対応で端末保存するようにした。保存は更新後のプレイから有効。すでに終了して失われたローカル進行は復元できない。
- blue・pink の起動や複数班の GPS／獲得操作などには UI コールバック内の同期通信が残る。回線不良時に画面が長く反応しなくなる可能性がある。ネイティブクラッシュとの因果は未確認。全画面の非同期化は今回実施していない。
- blue は実際の目的地座標がサーバーか端末に必要。コードが座標を受け取れるようには直したが、green の iPad を含む実機の保存内容や、稼働中 API の東京版データは未照合。座標未登録なら撮影後に進めない。
- purple は2地点目の到着時にローカルポイントをサーバーの班得点で上書きする。謎や攻撃で増減したポイントと一致しないことがある。配点・ゲーム設計に関わるため変更していない。
- 起動直後の GPS がまだ取れない場合には各ゲームで再試行が必要。実地の電波・位置精度・カメラ動作は Mac のテストでは評価できない。

朝の追加確認は、purple の地点到着→謎、green の地点に表示される半径、blue の撮影対象座標の有無、pink の手動 GPS 更新後の自動コイン収集を優先する。実際の地点獲得は本番の記録を変えるため、現地のプレイ時に確認する。

## red・purple・pink の進行保存

| ゲーム | 保存する進行 |
| --- | --- |
| red | 持ち物・武器の残り使用回数・所持容量・最大HPと現在HP・星ごとの撃破数・発見済み地点・撃破済みボス |
| purple | ポイント・ボスHP・残機・到着／謎の達成・出題済み問題・宝箱とアイテム・善玉くんの状態 |
| pink | コイン・チケット・次のコインまでの移動距離の端数・取得済みコインID |

- 保存先は Pythonista の `~/Documents/acamp-game-progress/`。Working Copy のリポジトリ外なので Pull によるファイルの入れ替えに影響されない。**同じiPad内での再開用**であり、端末間の同期機能ではない。
- 遊ぶ班・ゲーム・モード・設定上のセッションを分離し、サーバーから返った実際のセッションIDごとに進行を保持する。通信できない起動では最後に確認できたセッションを読み込み、接続後に別セッションと判明したらそのセッションの記録へ切り替える。
- 操作が確定した時点と通常の画面終了時に保存する。書き込みは一時ファイルから置換し、前の記録も `.bak` に残す。破損時は予備の記録、それも読めなければ初期状態で起動し、画面にその旨を表示する。保存失敗でゲームを終了させず、スタッフへ伝えるメッセージを表示する。
- red はモンスター選択画面から再開する。戦闘相手の残りHP、通常モンスターの配置・再出現待ちは復元しない。purple は確定済みのボスHP等は戻すが、謎のカウントダウンや演出の途中は復元しない。pink は終了中の移動をコインに換算しない。GPS座標自体は保存しない。
- purple の既存「リセット」は現在のセッションの保存と予備の記録を初期状態で置き換える。ライフ0直後、再開演出の前に終了した場合も、元のゲームオーバーのルールどおり初期状態から再開する。
- API管理操作で**同じセッションIDを使って**サーバーだけを初期化したことは端末から検出できない。別のゲーム回は新しいセッションIDで区別する。red・pink に新しいリセットボタンは追加していない。
- `diagnostics/red_battle_check.py` は保存・読み込みとも無効。本番の装備やHPを上書きせず、保存の実機確認にも使わない。

保存の実機確認は、通常ゲームで一つ操作した後の数値や持ち物を控え、Pythonistaを完全終了して同じゲームを開き直し、保持されていることを確認する。purple はリセット後にも開き直して確認する場合、**実際に進行を消す操作になる**ので本番進行では行わない。iPad のファイル書き込み・再起動での確認は未実施。

## iPad での短い確認

更新を共有リポジトリへ反映した後、Pythonista を完全終了してから Working Copy でリポジトリ全体を Pull し、同じ連携フォルダを Pythonista で開く。ファイル1個だけをコピーしない。

1. `diagnostics/red_battle_check.py` を実行する。位置への移動は不要。通信・得点登録はせず、テストの HP と持ち物はこの画面内だけで使う。

4. 「敗北」で攻撃し、結果画面から戻れることを確認。
5. 確認用画面を閉じ、通常は `day4_game_gallery.py` を実行。yellow は起動・開き直しで進行が消えないことを確認。「最初からやり直す」は確認のために押さない。

もし再び落ちたら、どの確認ボタンで、途中か結果表示か、Pythonista 全体が終了したかを記録する。ネイティブ原因の特定には iPad のクラッシュログが必要になる場合がある。
